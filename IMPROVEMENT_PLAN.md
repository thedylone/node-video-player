# Improvement plan

A prioritized list of fixes and improvements for this repo, written to be picked up and implemented across sessions.

## How to use this file

- Work top to bottom. Phase 1 items are bugs; do them before refactoring.
- Each item has an ID (e.g. `P1-03`). Use it in commit messages and branch names.
- When an item is done, tick its checkbox and add a short note (commit hash, or anything that changed from the plan). If an item turns out to be wrong or unnecessary, strike it through and say why rather than deleting it.
- Line numbers were recorded at commit `89e09df` and will drift. Functions and routes are named so you can find them again by searching.
- Findings came from reading the code; confirm each bug before fixing it. Use `npm ci` (not `npm install`) to install without changing `package-lock.json`. To run the server outside Vite: `npm run build && npm run build:server && npm start` (from the repo root; `PORT` defaults to 3000). For manual testing, point `DIRECTORY` and `DB_FILE` at a scratch folder with environment variables, which take precedence over `.env`. Add or update tests with each fix (see "Verifying changes").
- Keep changes small and in the style of the surrounding code (`log.info` / `log.error` from `src/server/log.ts` for logging, and `throw new HttpError(...)` in routes). Prettier sets the formatting (4 spaces, double quotes); run `npm run format`.

## Project overview

- Vite 8 + React 19 + React Router 7 client in `src/`. Node 22.22+ or 24.15+.
- Express server in [src/server/](src/server/) (modules listed under P3-01). [express-plugin.ts](express-plugin.ts) mounts `app` from [src/server/app.ts](src/server/app.ts) into the Vite dev server via `ssrLoadModule`, calls the exported `start()` (scan timers) and stops the old copy's timers when Vite reloads the module. [src/server/main.ts](src/server/main.ts) is the production entry: it serves `dist/`, calls `app.listen` and `start()`. `npm run build:server` bundles it to `dist-server/main.js`.
- Client fetch code and loaders are in [src/api/index.ts](src/api/index.ts); the `Video` type shared by both sides is in [src/shared/schema.ts](src/shared/schema.ts).
- Database is a JSON file (`DB_FILE`, default `db.json`) holding `{ [id]: Video }`. It is held in memory ([src/server/db.ts](src/server/db.ts)). `saveDatabase()` writes it (via `<DB_FILE>.tmp` and a rename) after every change and after the 60 s scan in `updateDatabase()` ([src/server/scan.ts](src/server/scan.ts)).
- Videos live in `DIRECTORY/<source>/<title>/*.mp4`. Thumbnails are generated by ffmpeg, one at a time, as `tn.png` in the title folder.
- Config comes from `.env` (untracked since P2-03; copy `.env.example`): `FFMPEG_PATH`, `FFPROBE_PATH`, `DB_FILE`, `DIRECTORY`, `PORT`.
- Tests (Vitest) sit next to the code as `*.test.ts(x)`; [src/server/test-server.ts](src/server/test-server.ts) loads a fresh server against a temporary folder. CI is [.github/workflows/ci.yml](.github/workflows/ci.yml). Lint config is [eslint.config.js](eslint.config.js), Prettier's [.prettierrc.json](.prettierrc.json).

### Server: [src/server/index.ts](src/server/index.ts)

- [x] **P1-01 Crash on first run with no `db.json`.**
  `jsonfile.readFileSync(DB_FILE)` (line ~29) throws if the file is missing.
  *Fix:* if the file doesn't exist, start with `{}`. Also fix the defaults `"/db.json"` and `"/videos"` (lines ~13-14), which point at the filesystem root; use `"db.json"` and `"videos"`.

Verified: with no `db.json` the server starts and writes it after the first scan, and a second start loads it.

- [x] **P1-02 Uptime ticker crashes when stdout is not a TTY.**
  `start()` calls `process.stdout.clearLine` / `cursorTo` every second (lines ~448-457). These are undefined when output is piped (pm2, Docker, `> log.txt`), so the interval throws repeatedly. *Confirmed* while testing P1-01: running with output piped crashes about 1 s after start with a `clearLine` TypeError.
  *Fix:* only run the ticker when `process.stdout.isTTY` is true, or remove it.
  *Done when:* `node dist/server/index.js > out.log` runs without errors.
  *Status:* done in `554ca73`. The ticker only runs when `process.stdout.isTTY`. Verified with stdout piped (the built server is now `dist-server/index.js`, see P1-07).

- [x] **P1-03 A stray file in `DIRECTORY` crashes the scan.**
  In `addDirToDatabase`, every entry from `fsp.readdir(DIRECTORY)` is treated as a source folder. A file like `.DS_Store` makes the nested `readdir` fail with `ENOTDIR`. `updateDatabase()` is called without `await`/`.catch` in `start()` and `setInterval`, so the rejection is unhandled and kills the process.
  *Fix:* use `withFileTypes` and skip non-directories at the source level, as is already done for titles. Wrap `updateDatabase` so errors are logged, not thrown. Also handle `jsonfile.writeFile` rejecting.
  *Done when:* putting a file directly inside `videos/` causes no error, and a forced write failure is logged without crashing the server.
  *Status:* done in `ecc7d57`. Confirmed the `ENOTDIR` crash first. `updateDatabase` catches everything and never prunes after a failed scan, so a missing or unreadable `DIRECTORY` can't empty the database. Verified with `videos/.DS_Store` and with `DB_FILE` in a folder that doesn't exist.

- [x] **P1-04 New videos in an existing title folder never show up.**
  In `addDirToDatabase`, `vids` is only set when a title is first added (`if (current.includes(...)) continue;`).
  *Fix:* on each scan, update `vids` for existing entries too, preserving `counter` and `tags`. Sort `vids` so the order is stable.
  *Done when:* adding `b.mp4` to an existing title shows it in the watch sidebar after the next scan.
  *Status:* done in `e9a4aa1`. Sorted in natural order (`2.mp4` before `10.mp4`). If every video is removed from an existing title, its `vids` becomes `[]` (the entry, counter and tags are kept, and the watch page shows "no videos found!"); the gallery still lists it.

- [x] **P1-05 Missing input validation lets bad data break search.**
  - `POST /api/tag` with no `tag` pushes `undefined` into `tags`. It is saved as `null`, and `getVideos` then throws on `x.toLowerCase()` for every request to `/api/videos`.
  - `POST /api/tags` accepts any type for `tags`.
  - `POST /api/count` with a non-numeric `num` stores `NaN` (which JSON-serializes to `null`).
  *Fix:* validate bodies. Require `tag` to be a non-empty trimmed string (but see P1-14 on how the client creates empty tags first), `tags` to be `string[]`, and `num` to be a finite integer. Return 400 otherwise. As a guard, make `getVideos` ignore non-string tags.
  *Done when:* `curl -X POST /api/tag -d '{"id":"<id>"}'` returns 400 and search keeps working.
  *Status:* done in `3299e8e`. Correction: the bad tag only broke requests with a search term (an empty search matches every title first). Beyond the plan:
  - `DELETE /api/tag` requires a string tag, but allows `""` so old empty tags can be removed.
  - `/api/count` and `/api/tags` return 404 for an unknown id. `/api/count` used to return 200 with `-1`, which is also a valid counter.
  - `/api/tags` trims tags and drops empty and duplicate ones. A bare string is rejected.
  - Loading the database drops `null`/empty tags left by the old code.
  - **New bug fixed:** ids were looked up with `database[id]`, so an id of `__proto__` reached `Object.prototype`. `POST /api/count {"id":"__proto__","num":1}` added an enumerable `counter` to every object, which broke search until restart. All lookups now go through `getVideo()`, which only matches own keys.
  - Adding tags from the UI is broken between this commit and P1-14, because the old client flow saves `""` first.

- [x] **P1-06 Production fallback route sends the file path as text.**
  `app.get("/*", (_, res) => res.send(frontendFiles + "/index.html"))` (line ~466) sends the path string, not the page.
  *Fix:* `res.sendFile(path.join(frontendFiles, "index.html"))`. Also give `app.listen` a default port (e.g. `Number(process.env.PORT) || 3000`) and log the URL.
  *Done when:* after `npm run build`, running the server and loading `/watch?id=...` directly renders the app.
  *Status:* done in `18aecef`. Before this, an unset `PORT` meant a random port. Unknown `/api/...` paths also fall through to `index.html` with 200 (see P3-04).

- [x] **P1-07 `build:server` likely produces a server that can't start.**
  The script compiles to CommonJS (`--module commonjs`), but `nanoid@5` only supports ES modules, so `require("nanoid")` fails. The project already has `"type": "module"`.
  *Fix:* build the server as ES modules (separate `tsconfig.server.json` with `module: NodeNext`, or bundle with esbuild/`vite build --ssr`), or run it with `tsx`. Add a `start` script.
  *Done when:* `npm run build && npm run build:server && npm start` serves the app.
  *Status:* done in `d4fbddf` with `vite build --ssr`, so no new dependency. Output goes to `dist-server/` (gitignored), not `dist/server/`: `express.static("dist")` would have served the server bundle, and `vite build` empties `dist/`. `vite.config.ts` turns off copying `public/` for the SSR build. `npm start` runs `node dist-server/index.js` from the repo root.

- [x] **P1-08 Edge cases in `/api/stream/:id`.**
  - `?index` is not checked. An out-of-range or non-numeric value builds a path ending in `/undefined`.
  - A suffix range like `bytes=-500` gives `start = NaN`.
  - `end` is not capped at `fileSize - 1`, and there's no `416 Range Not Satisfiable`.
  - `fs.statSync` blocks the event loop.
  - `Content-Type` is always `video/mp4`.
  *Fix:* validate `index` (400 if bad); parse ranges properly, including suffix ranges; cap `end`; return 416 for unsatisfiable ranges; use `fsp.stat`; derive MIME type from the extension. Also handle `stream.on("error")`.
  *Done when:* `curl -H "Range: bytes=-500"` returns 206 with the last 500 bytes and `?index=99` returns 400/404.
  *Status:* done in `835795b`. A non-numeric `?index` returns 400, an out-of-range one 404. Malformed or multi-range headers are ignored (200 with the whole file, as RFC 9110 allows). 200 responses now include `Accept-Ranges: bytes` too. Verified suffix, open-ended and over-long ranges byte-for-byte against the file, plus 416 and a file deleted after the scan.

- [x] **P1-09 Tag and count changes can be lost.**
  Changes only reach disk when the 60-second `updateDatabase` runs; a crash or restart loses them. Writes are not atomic, so a crash mid-write can corrupt `db.json`.
  *Fix:* add a `saveDatabase()` (debounced is fine) called after each change in `addCount`, `updateTags` and `deleteTitle`. Write to `db.json.tmp` and then `rename`.
  *Done when:* changing a tag and immediately restarting the server keeps the tag.
  *Status:* done in `59826cb`. Not debounced: each change awaits `saveDatabase()` before the response is sent, and saves made while one is running are combined into one more save. Verified with 20 parallel +1s and a new tag, then killing the server straight away: all were kept. No `.tmp` file is left behind.

- [x] **P1-10 Dev plugin problems: [express-plugin.ts](express-plugin.ts).**
  - The server module calls `start()` when it loads. Each time Vite reloads the module after an edit, a new set of `setInterval`s is created on top of the old ones.
  - The `catch` only logs and never calls `next(err)`, so failed requests hang.
  - The plugin has no types (`server` is implicitly `any`).
  *Fix:* export `start` and let the plugin call it once (or guard with a flag stored on `globalThis` and clear old intervals). Call `next(err)` in the `catch`. Type the plugin as Vite's `Plugin`.
  *Done when:* editing `src/server/index.ts` several times in dev still logs `database updated` only once per minute.
  *Status:* done in `29df47c`. `start()` returns a stop function. The plugin calls `start()` whenever `ssrLoadModule` returns a new copy of the module, stopping the previous copy first. Calling it only once would leave a reloaded module with its own `database` that is never scanned. The scan starts when the dev server starts listening. Verified with a script that edits the file three times, then introduces a syntax error (the request gets 500 instead of hanging) and fixes it: after more than 60 s only one periodic `database updated` appeared. The old copy keeps its timers until the first request after an edit.

- [x] **P1-11 Delete may never reach the server.**

- [x] **P1-12 Count and tag updates race with the data reload.**
  The buttons in `watch-sidebar.tsx` and `tag.tsx` are `type="submit"` inside the `<Form>` in [src/components/content.tsx](src/components/content.tsx). Clicking one fires the `fetch` and submits the form (which reloads the route data) at the same time, so the reload can return the old value.
  *Fix:* use React Router `action`s with `useFetcher` (or `fetcher.submit`) so data reloads after the change finishes. Make the non-form buttons `type="button"`.
  *Done when:* clicking +1 quickly several times always shows the correct count.
  *Status:* done in `3faf14f`, **differently from the plan**: buttons are `type="button"`, and each handler awaits its API call and then calls `useRevalidator().revalidate()`. A newer revalidation cancels an older one, so the last reload always starts after the last write. `useFetcher` wasn't used because a fetcher drops its in-flight submission when it is submitted again, so a rapid click could skip the reload after the last write. Verified by driving `@remix-run/router` against the real server with random delays: the old pattern showed a stale count in 9 of 15 runs, the new one in 0 of 15. Not clicked through in a browser. Moving these calls to route `action`s fits better after P2-05.

- [x] **P1-13 Search terms are not URL-encoded.**

  *Fix:* use `encodeURIComponent`. The cleaner fix is to move search to a query string (see P2-04).
  *Status:* done in `115fcb5`. Verified that the encoded paths match `/search/:query` and that the loaders' `url.pathname` reaches Express decoded correctly for `?`, `#`, `/`, `%` and spaces. React Router 6.16 decodes the path twice, so a term containing `%` logs a "malformed URL segment" warning in dev; results are still correct because the loaders read `url.pathname`, not `params.query`. P2-04 removes this.

- [x] **P1-14 Using array indexes as list keys shows wrong tag values.**
  Tags and gallery items use `key={index}`. `Tag` uses an uncontrolled `defaultValue`, so deleting a tag can leave the wrong text in the remaining inputs.
  *Fix:* key tags by `tag` and videos by `video.id`. The "add tag" flow (`TagAdder` adds `""`, then `onBlur` removes `""` and adds the new value) is fragile and allows multiple empty tags. Replace it with a local input that only calls `addTag` once a value is entered.
  *Status:* done in `9a91cbe`. Sources and video files are keyed by name as well. `Tag` is now display-only (a read-only controlled input that searches on click, plus ✕). `TagAdder` is an "add tag" input that adds on Enter or +. It stops its change events from reaching the content `<Form>`, whose `onChange` submits the form. Type-checked and built; not clicked through in a browser.
